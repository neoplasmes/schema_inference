# Производительность редактора

Итоговый изолированный прогон снимка `f42e070` завершился с кодом 0: три нагрузки, 12 фаз и 968 callbacks с настоящими WebGL draw calls. Ошибок страниц нет. Снимки `stress.png`, `dense.png` и `paged.png` просмотрены: содержимое нарисовано, benchmark не измерял пустую доску. Предварительный прогон с HMR в эти результаты не входит.

В измеренной программной среде 60 FPS не достигнуты: даже при непрерывных synthetic событиях медианные интервалы рисования составили 200,9-302,6 мс вместо бюджета 16,7 мс. Аппаратный критерий среднего ноутбука остаётся непроверенным. Длительные интервалы и синхронная CPU работа измеряются раздельно; одно нельзя подменять другим.

## Метод

Все сценарии используют viewport 1440×900, DPR 2 и уменьшение анимации. Основная нагрузка `stress` содержит ровно 2000 карточек, 4000 связей и 16000 строк с латиницей и кириллицей. Скрипт проверяет эти количества через доступный только для чтения `window.__editorPlayground.read()`. `dense` содержит 120 карточек по 18 строк; `paged` содержит 32 карточки по 50 загруженных строк с признаком неполной коллекции из 2000 элементов. Последний сценарий проверяет стоимость отображения окна страниц; этот benchmark не измеряет настоящий HTTP transfer, серверное раскрытие и задержку загрузки следующей страницы.

После готовности редактора и шрифтов выполняется секунда покоя, затем два разных вида ввода. Pan проходит 480 px в сторону и возвращается с остатком 12 px, чтобы последовательные фазы не уходили за пределы плотной сцены. Zoom проходит примерно от исходного масштаба до 2,2 от него и обратно. Каждый жест состоит из 80 шагов:

1. Trusted Playwright: pan средней кнопкой мыши и zoom с Control+wheel. Это настоящие браузерные события через протокол автоматизации. Их интервалы включают темп Playwright, браузера и compositor, поэтому время между ними нельзя называть чистой стоимостью renderer.
2. Continuous DOM: по одному синтетическому WheelEvent на requestAnimationFrame, отдельно для pan и zoom. Эти события непрерывно нагружают тот же обработчик редактора без отдельных команд драйвера на каждый шаг. Они позволяют исследовать throughput, но не подтверждают физический трекпад или устройство ввода.

Глобальный тестовый hook считает WebGL draw calls внутри каждого callback requestAnimationFrame. В распределение интервалов входят только callbacks, действительно отправившие команды рисования. Пустой callback не становится кадром renderer. Счётчик `renderedFrames` редактора дополнительно должен увеличиться минимум на 20; pan обязан изменить камеру. Для каждого шага сохраняются исходные данные, median и p95 интервалов, длительность синхронного CPU callback, draw calls и задержка от первого ожидающего события до завершения CPU submission.

Median показывает середину распределения, p95 показывает время, в которое укладываются 95% измерений; оставшиеся 5% медленнее. Поэтому p95 помогает увидеть периодические задержки, которые скрывает одно среднее число.

CPU submission не означает завершение GPU. Задержка ввода не является временем появления пикселя на мониторе. Отдельный CDP CPU profile записывается после основных метрик; его overhead в эти метрики не входит. JSON содержит JS heap до и после жестов без принудительного garbage collection, видимые карточки/связи/текст из renderer и созданные/удалённые WebGL texture, buffer, shader и другие handles. Количество handles не является расходом GPU в байтах. Счётчика уничтоженных Pixi display objects в текущем публичном diagnostic нет; WebGL delete counts не заменяют его.

В покое каждая сцена дала 60 RAF callbacks и 0 draw frames за одну секунду. Это подтверждает отсутствие постоянного рисования неподвижной доски в этом прогоне; 60 пустых RAF callbacks не объявляются 60 FPS редактора.

Trusted input приходит через драйвер и может оказаться близко к следующему render callback. Continuous DOM выдаёт событие из предыдущего RAF, поэтому его input-to-submission включает ожидание следующего рисования. Эти две величины не являются взаимозаменяемыми измерениями задержки физического устройства. У continuous фаз уже нет отдельной Playwright-команды между каждым событием, но большие интервалы сохраняются.

Порядок фаз фиксирован: trusted pan, trusted zoom, continuous pan, continuous zoom. Первый zoom работает с менее прогретыми кешами. Поэтому разницу CPU между двумя zoom нельзя приписывать только способу доставки события.

В dense и paged одновременно показывается окно до 10 строк карточки; полный набор 18 или 50 загруженных строк не превращается в такое же количество постоянно рисуемых строк. ## Профили и локализация задержек

Основные `stress.cpuprofile`, `dense.cpuprofile`, `paged.cpuprofile` записаны на отдельном pan после метрик. Они не включены в таблицу кадров. В stress `queryInto` получил 16,3 мс self samples за 14,36 с профиля, то есть 0,11%; в dense крупнейшая именованная функция `updateTransformAndChildren` получила 31,0 мс за 14,08 с, то есть 0,22%. Эти pan profiles не показывают дорогого полного JavaScript обхода загруженных 2000 карточек на каждом кадре. Метка `(program)` занимает 98,2-98,6% samples, но она сама по себе не является GPU таймером и не локализует ожидание внутри браузера.

Отдельная пятисекундная выборка `/proc` во время изолированного прогона сохранена в `process-cpu-sample.json`. SwiftShader GPU process потратил 57,93 CPU-секунды за 5,00 wall-секунды, около 1158% CPU, или 11,6 логических ядер. Выборка могла пересекать profiling/setup, поэтому она не является чистой стоимостью конкретной фазы.

Измеренные факты: большие интервалы сохраняются при continuous DOM; медианный CPU callback обычно занимает 0,7-3,6 мс; отдельный software GPU process интенсивно использует CPU. Вывод: значительная часть задержки этого окружения находится вне измеренной синхронной JavaScript работы и согласуется с затратами software graphics/backend. Точная доля raster, compositor, driver queue и GPU completion не измерена. Подменять эти интервалы временем выполнения `sync()` нельзя.

### Первый dense zoom

Хвост первого trusted dense zoom воспроизведён в отдельном свежем browser context: 80 draw frames, CPU callback median 4,9 / p95 70,4 мс, максимум 83,0 мс. Основной benchmark выше остаётся источником итоговых 4,3 / 66,8 мс: CPU profiler и дополнительные timing wrappers в диагностическом запуске добавляют overhead.

Артефакты: `dense-zoom.cpuprofile`, `dense-zoom-profile.json`, `dense-zoom-profile.png`, воспроизводимый `dense-zoom-profile.mjs`. При уже работающем HTTP editor из корня проекта:

```sh
/home/neoplasmes/.proto/tools/node/22.15.0/bin/node apps/editor/visual/actual/perf/dense-zoom-profile.mjs
```

В sampled ветке renderer `sync` набралось 1851,9 мс inclusive. Из них `_updateGpuText` занял 1515,6 мс, около 82% этой ветки. Таблица показывает вложенные участки профиля; inclusive значения нельзя складывать между строками.

| Участок Pixi text pipeline | Self samples, мс | Inclusive samples, мс |
|---|---:|---:|
| `_updateGpuText` | 16,4 | 1515,6 |
| `getTexture` | 167,8 | 1442,1 |
| `getCanvasAndContext` | 12,1 | 701,9 |
| `CanvasTextMetrics.measureText` | 41,9 | 350,3 |
| `_renderTextToCanvas` | 52,1 | 337,3 |
| `texSubImage2D` | 237,4 | 237,4 |

Создано 408 дополнительных textures: 2705 до zoom и 3113 после. Отдельно обёрнутые 408 вызовов `texImage2D` имели максимум 0,2 мс, однако profile обнаружил 237,4 мс в `texSubImage2D`. Следовательно, измерение только `texImage2D` не описывает всю загрузку текста.

Связь с исходниками подтверждена: `board/render/create_board_renderer.ts`, `setViewport`, ставит timeout 160 мс и затем вызывает `view.setResolution()` для материализованных карточек. `CardView.setResolution()` передаёт новое разрешение всем удерживаемым labels. В этом прогоне между событиями zoom около 333 мс, поэтому timeout успевает срабатывать между шагами и вызывает повторную подготовку Canvas text textures. Это согласуется с измеренной цепочкой `_updateGpuText` / `getTexture` / canvas measurement / texture upload и локализует CPU хвост.

Первый zoom создал новые textures, последующий прогретый synthetic zoom новых textures не создал и имел CPU p95 10,4 мс. Отсюда нельзя выводить одинаковую цену каждого zoom или поведение аппаратного браузера: при более частом вводе timeout может дождаться реального окончания жеста. Реакция text-resolution policy в медленной software среде подтверждена, необходимость менять её на целевом GPU ещё требует отдельного измерения.

## Следующие проверки и границы результата

1. Повторить тот же workload и DPR 2 на целевом ноутбуке с аппаратным WebGL, затем на production build. Это необходимое измерение для критерия 60 FPS; текущий SwiftShader результат его не заменяет.
2. Записать GPU/raster/compositor trace, если большие интервалы повторятся на аппаратном backend. Контрольный DPR 1 полезен для диагностики стоимости pixels, но не заменяет исходный DPR 2 benchmark.
3. Для подтверждённого CPU хвоста первого dense zoom сравнить редкие фиксированные text-resolution уровни либо обновление текстур ограниченными порциями после завершения жеста. Проверять качество текста и повторить cold/warm zoom; изменение renderer в рамках этого performance-прогона не выполнялось.

Этот benchmark не измеряет физический pinch, IME, появление пикселя на мониторе, GPU bytes/completion, настоящий HTTP transfer и server persistence. Paged fixture измеряет стоимость представления уже загруженного окна, а не серверное раскрытие следующей страницы. Отдельная correctness-проверка жизненного цикла не заменяется этими heap snapshots. Все числа относятся к указанным viewport, DPR, fixture density, development build и SwiftShader среде; аппаратные 60 FPS остаются открытым критерием.
